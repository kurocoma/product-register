# product-research-autofill — 商品リサーチ自動反映

最小のユーザー入力から商品情報を自動調査し、商品登録アプリ
（`C:\Users\hppym\dev\product-register`）の統一入力フォーマット
（`docs/spec.md` §3、68列）を埋めて、ユーザー確認のうえアプリに反映するスキル。

## 役割分離（固定）

| 役割 | 担当 | 仕事 |
|---|---|---|
| 司令官 | メインセッション（Fable） | 入力の正規化・調査タスクの分割・結果の信憑性判定・文章生成・最終判断・ユーザー確認・アプリ反映 |
| 調査員 | Agent ツールで **`model: opus`**（Opus 4.8）を指定したサブエージェント | Web 調査と出典つき事実収集のみ（並列起動。フィールド値の最終決定はしない） |

分割・並列化・調査プロンプトのテンプレは [research-pipeline.md](research-pipeline.md)。

## ユーザー入力（8項目）

| # | 項目 | 区分 | 形式・例 | 入力仕様 |
|---|---|---|---|---|
| 1 | 作成する入数 | **必須** | `1本、3本、6本` | 複数指定可。1入数 = 1 SKU（グリッド1行）になる |
| 2 | 売価（税抜） | **必須** | `1本500円、3本1300円、6本2500円` | **入数ごと**に指定。税抜で受け取り、税率確定後の税込換算値を確認ステップで提示して承認を得る |
| 3 | 配送方法 | **必須** | `宅急便` / `ネコポス` / `レターパック` | **入数ごとに異なってよい**（例: 1本はネコポス、3本以上は宅急便）。配送方法セット番号への対応は `docs/spec.md` §8（4=特定送料 / 5=メール便 / 6=レターパックプラス）で解決し、対応が曖昧なら確認ステップで質問する |
| 4 | JANコード | **必須**（「JANなし」申告可） | `4955028002542` | 13桁（アプリの `jan_code` は13桁必須: `webui/lib/product/schema.ts`）。JANの無い商品は「JANなし」と**明示申告**してもらう（無回答のまま黙って進めない） |
| 5 | 商品名 | **必須** | `GIANTSボトル 10年貯蔵古酒 720ml 25度` | `product_name` にそのまま入る。掲載商品名は自動補完（手修正可） |
| 6 | 送料区分 | **必須** | `1本は送料1050円、3本・6本は送料無料` | **入数ごとに異なってよい**。「送料◯円」と金額が付く入数は 送料別+個別送料 として扱う |
| 7 | 納期管理番号 | **必須** | `1` | `docs/spec.md` §8 納期管理番号マスタの番号（例: 1=2〜4日以内で発送） |
| 8 | 参考URL・画像・添付ファイル | 任意 | URL複数・ファイルパス可 | ユーザー提供資料は**一次情報として最優先で採用**する（reference.md の信憑性ポリシー）。無くても調査は可能（あれば精度が上がる） |

区分の理由: 1〜7 はこれが無いと登録データ（SKU行・価格・配送・納期）を構成できないため**必須**。
8 は無くても調査可能なため**任意**（あれば一次情報として精度向上）。JAN は JAN の無い商品が実在するため
「JANなし」の明示申告を許す（申告があれば充足扱い。無回答のまま進めるのは不可）。
1〜7 に不足があれば手順2 の充足チェックで**不足分だけを1回にまとめて質問**する
（項目→質問文・選択肢の対応表は [reference.md](reference.md) §6）。

## 手順

1. **入力受付** — 8項目を受け取り、「入数 ×（売価・配送方法・送料区分）」の対応表に正規化する。
2. **必須項目の充足チェック（調査より前）** — 正規化結果を上の8項目表と突き合わせ、必須（1〜7）の不足を検出する。
   不足があれば**不足している項目だけを、1回のやり取りにまとめて質問**する — 選択肢を列挙できる項目
   （配送方法・送料区分・納期管理番号）は AskUserQuestion ツール（選択肢提示）、自由記述の項目
   （入数・売価・JAN・商品名）は番号つき質問リスト。質問文・選択肢の対応表と実例は
   [reference.md](reference.md) §6。回答を既提供分にマージして再チェックし、
   **必須項目がすべて埋まるまで調査（R1〜R4）を開始しない**（8 は任意 — 無くても止めない。
   JAN は「JANなし」の明示申告で充足扱い）。値はあるが曖昧なもの（例: 配送方法→セット番号の対応）は
   調査を止めず、確認ステップ（手順5）で解消してよい。
3. **調査** — [research-pipeline.md](research-pipeline.md) に従い、`model: opus` の調査サブエージェントを **1メッセージで並列起動**する（R1 商品基本情報 / R2 ユーザー提供資料 / R3 モールカテゴリ / R4 コンテンツ素材）。
4. **判定・生成** — [reference.md](reference.md) の「AI判別17項目」の定義（入力ソース→判定手順→出力先）に従って各フィールドを決定する。
   - 信憑性ポリシー（reference.md §2）を満たさない情報は**掲載しない**（空欄+要確認リスト行き）。
   - 文字数上限（reference.md §3、repo内出典つき）は**コードで実測**してから確定する（目視で数えない）。
5. **ユーザー確認（必須・スキップ禁止）** — 次を表で提示し、**承認を得るまでアプリに反映しない**:
   生成した全フィールド値 / 画像枚数と各画像の内容提案 / 税込換算後の売価 / 要確認リスト（出典が足りず空欄にした項目・曖昧な対応）/ 出典一覧。
6. **反映** — 承認後、[reference.md](reference.md) §5「アプリへの反映経路」で反映する:
   - 推奨: 一括登録グリッド用 TSV を生成 → WebUI `/bulk-register` に貼り付け → 保存（自動補完が働く）→ `POST /api/register/bulk/[mall]`（**dryRun 既定 true** で内容確認 → `dryRun: false` を明示して実登録）
   - 代替: 統一入力CSV（68列）→ `python -m product_register convert`（Phase 1 CLI）
