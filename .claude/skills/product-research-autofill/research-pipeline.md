# research-pipeline — 司令官(Fable)と調査サブエージェント(Opus 4.8)

## 役割分離

- **司令官 = メインセッション（Fable）**: 入力の正規化、調査タスクの分割、サブエージェントの並列起動、
  結果の信憑性検証（reference.md §2）、矛盾の解決、フィールド値の決定と文章生成、文字数の実測、
  ユーザー確認、アプリ反映。**最終判断はすべて司令官が行う**。
- **調査員 = Agent ツールのサブエージェント**: 必ず **`model: opus`（Opus 4.8）** を指定し、
  `subagent_type: general-purpose` で起動する（WebSearch / WebFetch を使った Web 調査のため）。
  調査と出典つきの事実収集のみを行い、フィールド値の最終決定・文章の確定はしない。

## タスク分割（並列4系統）

**起動条件（充足ゲート）**: SKILL.md 手順2 の必須項目充足チェックを通過していること。
**必須項目（ユーザー入力1〜7）がすべて埋まるまで R1〜R4 の調査を開始しない**
（8 参考URL・画像・添付は任意。JAN は「JANなし」の明示申告で充足扱い。
値はあるが対応が曖昧な項目は調査を止めない — 確認ステップで解消（SKILL.md 手順2）。
不足時の質問テンプレは reference.md §6）。

R1〜R4 は互いに独立（共有状態なし・ファイル編集なし）なので、**1メッセージで同時に起動**する。
R2 はユーザー提供資料（URL・画像・添付）がある場合のみ起動する。

| ID | 調査系統 | 渡す入力 | 返させる内容 |
|---|---|---|---|
| R1 | 商品基本情報: JAN検索 → GS1事業者/メーカー特定 → メーカー公式ページ → スペック収集 | JANコード・商品名 | メーカー名 / ブランド名 / 内容量 / 度数 / 原材料 / 製造者 / 発売・受賞情報。各値に source_url |
| R2 | ユーザー提供資料の精読（一次情報の抽出） | 参考URL・画像・添付ファイルのパス | 資料内の事実の一覧（原文の言い回しも保持。説明文生成の主素材になる） |
| R3 | モールカテゴリ調査: 楽天市場で同一JAN/類似商品を検索 → 売場（ジャンル）候補化 | JANコード・商品名 | 楽天ジャンル候補2〜3件（ジャンルID・パス・根拠となる商品URL・確信度） |
| R4 | コンテンツ素材: 訴求点・FAQ・SEOキーワード・類似商品の見せ方 | 商品名（R1の結果は渡さず独立に調査） | キャッチコピー素材 / 画像構成のヒント / 検索キーワード候補（出典つき） |

ローカルファイルの参照（`docs/ichiba_attribute_list_20260421.csv` でのジャンルID実在確認・必須属性の列挙、
`docs/rakuten_yahoo_category_mapping.csv` の対応確認）は**司令官が自分で行う**（サブエージェントに委ねない）。

## R3 のフォールバック（JS レンダリング対策）

楽天市場の検索結果・商品ページは JS レンダリングが強く、素の WebFetch では商品リストが
取れないことがある。R3 は次の**切替条件**のいずれかに当てはまったら、素の WebFetch をやめて
**browser-fetch skill（Playwright。JS レンダリング後のページ内容を取得）**に切り替えて同じ調査を続行する:

- 取得結果に商品リストが含まれない（商品ページ URL `item.rakuten.co.jp/…` やジャンルのパンくずが 1 件も無い）
- 本文が空・数行のみ、または「JavaScript を有効にしてください」等の案内だけが返る
- 403 / CAPTCHA 等でブロックされ内容が取得できない

browser-fetch でも取れない場合は 1 回だけ再試行し、それでも不可なら R3 は「調査不能」として
要確認リストに明示する（勝手にジャンルを埋めない。下記「失敗時の扱い」と同じ原則）。

## サブエージェント・プロンプトテンプレ

Agent ツール呼び出し例（R1）。`{...}` を実値に差し替える:

```
subagent_type: general-purpose
model: opus
prompt: |
  あなたは商品情報の調査員です。調査と出典つきの事実収集だけを行い、推測で埋めないでください。
  対象商品: {商品名} / JANコード: {JANコード}

  タスク:
  1. JANコード検索（"{JANコード}" をそのまま検索）と GS1 事業者情報からメーカーを特定する
  2. メーカー公式サイトの該当商品ページを見つける
  3. 次の項目を収集する: メーカー名 / ブランド名 / 内容量 / アルコール度数 /
     原材料 / 製造者と所在地 / 発売・受賞情報 / その他の規格値

  出力（次のJSONのみを返す）:
  {"findings": [{"field": "メーカー名", "value": "...", "source_url": "https://...",
                 "source_type": "official|secondary|user", "confidence": "high|medium|low"}],
   "unknown_fields": ["確認できなかった項目名"],
   "notes": "補足（矛盾する情報を見つけた場合はここに両論併記）"}

  規則:
  - わからない項目は unknown_fields に入れる。値をでっち上げない。
  - 可能な限り公式ソース（メーカー・業界団体・公的機関）を優先する。
    非公式ソースしか無い値は confidence を low にする。
  - 各 value には必ず source_url を付ける（付けられない値は返さない）。
```

R2/R3/R4 も同じ骨格で「タスク」節を差し替える:

- **R2**: 「次のURL/ファイルを読み、商品に関する事実をすべて抽出する: {URL一覧}」。
  source_type は `user` 固定。原文の特徴的な言い回し（キャッチコピー素材になる文）も notes に残させる。
- **R3**: 「楽天市場で JAN {JANコード}・商品名 {商品名} の同一/類似商品を検索し、
  それらが属する楽天ジャンル（パンくず）を2〜3候補、根拠商品URLつきで返す」。
- **R4**: 「{商品名} と同種商品の売り方を調査し、訴求点・よくある質問・検索キーワード候補・
  商品画像の典型構成を出典つきで返す」。

## 統合手順（司令官）

1. 各エージェントの findings を出典タイプで検証する:
   `user` / `official` は採用候補、`secondary` は独立2ソースの一致を確認（reference.md §2）。
2. 矛盾があればユーザー提供資料 → 公式 → その他の順に優先。解けない矛盾は要確認リストへ。
3. R3 のジャンル候補はローカルの `docs/ichiba_attribute_list_20260421.csv` で実在確認し、
   必須属性を列挙する（reference.md §1 #17）。
4. reference.md §1 の17項目定義に従って各フィールドを決定・生成する。
5. 文字数上限（reference.md §3）をコードで実測する。
6. SKILL.md 手順5（ユーザー確認）→ 手順6（反映）へ進む。

## 失敗時の扱い

- サブエージェントが返らない / JSON が壊れている → **1回だけ**再起動する。
  それでも欠ける系統は「調査不能」として要確認リストに明示する（勝手に埋めない）。
- R1 と R2 の値が食い違う場合はユーザー提供資料（R2）を優先し、食い違いを確認ステップで報告する。
