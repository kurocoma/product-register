# 03. UX・情報設計（ステップ4 ／ 最終出力5）

目的: ユーザーの目的ごとに画面とナビを再編する。**機能は削除せず、入口を整理し、既存URLを壊さず段階移行**する。

## 4.1 現在の情報設計の問題（確認済み）

根拠: `components/nav/SideNav.tsx`（15項目フラット）、`app/(main)/help/page.tsx`（12画面のTOC）、各 `page.tsx`。

| 問題 | 具体 | 根拠 |
|---|---|---|
| メニュー過多 | トップレベルに15項目。低頻度（マスタ取込・関連商品抽出・テンプレート管理・ルール監査・設定）まで並列 | `SideNav.tsx` `items` |
| 重複した入口 | 「取込」が複数（一覧の `MallImportByCode` / `/migrate` / `/related-import` / `/bulk-images` の楽天読込）。「反映」も一覧・編集・一括の3系統 | `products/page.tsx`, `/migrate`, `/related-import`, `/bulk-images` |
| 名前と役割のズレ | ナビ「商品編集」→ 実体は `/products/new`（新規作成）。既存編集は一覧/履歴から `/products/[id]` | `SideNav.tsx:10` |
| 低頻度機能が目立つ | 「マスタ取込」「関連商品抽出」は価格改定の下調べ用（低頻度）だがトップに露出 | `help` の説明 |
| 同目的が複数画面に分散 | CSV/画像/登録/取込が「単品版（編集画面パネル）」と「一括版（専用ページ）」に二重化 | `ProductEditView.tsx`（右カラム4パネル）↔ `/csv` `/bulk-images` `/bulk-register` |
| 発見性の破綻 | ナビにあるがヘルプ未掲載: ルール監査・画像一括アップロード。設定は空実装なのに掲載 | `help` `SCREEN_TOC` vs `SideNav` |

## 4.2 新しいナビゲーション案（階層構造）

設計方針: **ユーザー目的でグループ化 / トップレベルを絞る / 低頻度は「その他・設定」配下 / 同目的はタブ・モード切替で統合 / 危険操作を分離**。既存URLは維持し、ナビの見せ方だけを再編（段階移行は 4.5）。

```
■ ダッシュボード            (/)                      … 現状把握・アラート

■ 商品                                              ← 日常作業の主戦場（目的: 作る・直す・出す）
   ├ 商品一覧                (/products)             … 探す・価格編集・反映・選択CSV
   ├ 新規作成                (/products/new)         ← ラベルを「新規作成」に（現「商品編集」）
   └ 商品編集                (/products/[id])        … 一覧/履歴から遷移（ナビ直下には出さない）

■ 一括作業                                          ← 複数商品をまとめて（目的: 量をさばく）
   ├ 一括登録（グリッド）     (/bulk-register)
   ├ 画像一括アップロード     (/bulk-images)          ← ヘルプにも追加
   ├ CSV ダウンロード        (/csv)
   └ 楽天→Yahoo 一括移行      (/migrate)              ← 「一括作業」下に集約

■ 取込・関連付け                                    ← データを入れる（目的: 元データ整備）
   ├ 関連商品（セット）取込   (/related-import)
   ├ マスタ取込              (/masters)
   └ 関連商品抽出            (/masters/related)      … マスタ取込のサブ（タブ化候補）

■ 品質・監査                                        ← 出す前の点検（低頻度）
   └ ルール監査              (/rule-audit)           ← ヘルプにも追加

■ その他
   ├ テンプレート管理        (/templates)
   ├ 作業履歴                (/history)
   ├ 設定                    (/settings)             … 実装まで「準備中」を明示 or 非表示
   └ ヘルプ                  (/help)
```

- トップレベルを **6グループ**（ダッシュボード/商品/一括作業/取込・関連付け/品質・監査/その他）に集約。15フラット→意味のある階層。
- 破壊的操作（一括移行・一括登録の commit）は各画面内で dry-run→本実行の2段構え（既存踏襲）。ナビ上は「一括作業」に隔離し誤操作を減らす。
- 設定は空実装（`settings/page.tsx`）。実装までは「その他」配下＋「準備中」明示、またはナビ非表示（要判断・機能削除ではない）。

## 4.3 画面統合案

| # | 統合前 | 統合後 | 統合方法 | ユーザーへの影響 | 実装上の注意 |
|---|---|---|---|---|---|
| U1 | 一覧の一括CSV導線（`ProductList` の「選択を一括CSV出力」）＋ `/csv` | `/csv`（選択引継ぎパラメータで一本化） | 一覧は選択→`/csv?ids=…`へ渡すだけに。CSV生成UIは `/csv` に集約 | 動線は同じ。生成UIが1箇所に | 既存の「選択引継ぎ」実装を尊重。URL互換維持 |
| U2 | 編集画面 `CsvDownloadPanel`（単品CSV）＋ `/csv`（一括） | 「CSV」機能を1コンポーネントに（単品=1件選択の一括） | 共通CSVコンポーネントを単品/一括で再利用 | 単品DLは編集画面に残しつつ内部実装を共有 | `api/csv/[mall]/[id]` と `api/csv/bulk` の契約は当面維持 |
| U3 | 編集画面 `ImageUploadPanel`（単品）＋ `/bulk-images`（一括） | 画像アップロードUIの共通化（単品=1商品の一括） | パネルとページで同一アップロードコンポーネントを共有 | 見た目は現状維持、実装重複を解消 | R-Cabinet/Yahoo/Shopify 経路差を吸収する共通層が必要 |
| U4 | 編集画面 `RegisterPanel`（単品反映）＋ `/bulk-register`（一括） | 反映ロジックを共有（UIは単品/一括で別のまま可） | `lib/register/` を単一の正本にし両UIが呼ぶ | UIはそのまま、内部の二重実装を統合 | dry-run→commit の状態管理を共通化 |
| U5 | 取込の入口が分散（一覧 `MallImportByCode` / `/migrate` / `/related-import` / `/bulk-images` 楽天読込） | 「取込」の概念を明確化（コード指定取込 / 移行取込 / セット取込 / 画像取込） | 各入口は残すが、共通の取込サービス（`lib/converters/mall-import` 系）を正本化 | 入口ラベルを目的別に統一 | `api/fetch` `api/import` の役割整理（02の重複調査） |
| U6 | `/rule-audit`（検出）＋ 編集内 codex-normalize（修正） | 「品質・監査」動線として連結（検出→該当商品編集→codex修正） | 監査結果の各行から編集へ（既存導線）＋編集内で修正を促す | 検出と修正が1フローに | 両者とも `lib/rule-audit/` 配下。過度な統合はしない（別責務） |
| U7 | `/masters`（取込）＋ `/masters/related`（抽出） | 1画面のタブ（取込 / 抽出） | 同一データ(統合台帳)への操作をタブ集約 | 行き来が減る | URLは両方維持（タブのディープリンク） |

> **統合の原則**: 「見た目が似ている」だけで即共通化しない。単品/一括は **ユーザー体験としては別画面のまま**、**内部ロジック（`lib/`）だけを正本1つに統合**する方針（詳細は 04・05）。業務的に意味が異なる取込（現物取込 vs マスタ取込）は統合しない。

## 4.4 主要ユーザーフロー（開始→完了の画面遷移）

1. **新規商品を1件作って両モールへ出す**
   `/products/new`（テンプレ選択可）→ 入力＋自動保存 → `/products/[id]` → 画像アップロード → 楽天登録(dry-run→commit) → Yahoo画像lib転送 → Yahoo登録 → 一覧で反映確認。
2. **既存商品の価格改定**
   `/masters/related`（値上げ対象と関連セットを洗い出し）→ `/products` 検索 → インライン価格編集（自動保存）→ 行「反映」または選択→一括反映。
3. **楽天の既存商品をYahooへ横展開**
   `/migrate` → 楽天から取込 → カテゴリ自動変換（未対応は手入力）→ dry-run → Yahoo登録。
4. **まとめて新規登録**
   `/bulk-register` グリッド入力（貼付）→ カテゴリ/属性自動補完 → dry-run → commit → 失敗分のみ再実行。
5. **CSV運用（API未対応の作業）**
   `/products` で絞り込み・選択 → `/csv` → 5形式ZIP。
6. **出品前点検**
   `/rule-audit` → 違反行から `/products/[id]` → codex提案で修正 → 反映。

## 4.5 段階的移行案（既存URL・操作を壊さない）

情報設計の変更は **ナビの再グルーピングから**始め、URL・画面本体は据え置く。順序:

1. **S0（無risk）**: `SideNav.tsx` の並びを 4.2 の6グループへ再編（見出し＋インデント）。URL変更なし。ラベル「商品編集」→「新規作成」。**ロールバック=1ファイル revert**。
2. **S1**: ヘルプ `SCREEN_TOC` に「ルール監査」「画像一括アップロード」を追加、設定の扱いを明記。ナビとヘルプの整合を回復。
3. **S2**: `/masters` と `/masters/related` をタブ統合（両URL維持のディープリンク）。
4. **S3**: 内部ロジックの正本化（U2〜U5）を **UIを変えずに**進める（04・05 の feature-first 移行と同期）。UIの見た目は最後まで不変。
5. **S4**: 一覧⇔CSV の選択引継ぎ（U1）を1本化。`/csv?ids=` の互換を保つ。

> いずれの段階も **機能削除ゼロ**・**URL維持**・**1ステップ=小PR**。ナビ変更（S0/S1）と内部統合（S3）を分離し、UX変更と構造変更のリスクを混ぜない。
